# Три режима Miro Full Exporter

[English](WORKFLOW_MODES.md) | **Русский**

Меню **Workflow** в GUI задаёт, кто выполняет действия в браузере Miro. При
экспорте из Miro режимы используют общий REST-конвейер, необязательное
объединение REST/Web SDK, загрузку вложений и конвертацию Canvas. Для
конвертации готового JSON подключение к Miro не нужно. Результат охватывает
публичные API Miro, а не скрытые внутренние данные. **Экспорт данных** сохраняет
JSON и вложения в любую папку. **Для Obsidian** дополнительно преобразует данные
в Canvas и требует папку внутри хранилища. Miro Canvas предлагается в результате
как дополнительный способ работы с экспортом.

| Режим | Что выполняется автоматически | Где может понадобиться человек |
|---|---|---|
| **Manual** | Конвертация и проверка после **Run pipeline** | Создание Miro app, OAuth, выбор доски и скачивание Web SDK JSON |
| **Code automation** | REST items и comments, обязательные вложения, конвертация и проверка; этапы видны в журнале | Первое подключение Miro; необязательный Web SDK capture |
| **Agent** | Настроенный локальный агент пытается выполнить шаги в браузере, REST и Web SDK экспорт и проверить Canvas | Вход, MFA, одобрение администратора или недоступный браузер |

## Ручной режим

Выберите источник и папку Canvas в GUI. Для максимально доступного экспорта
запустите [Web SDK exporter](../tools/miro_websdk_exporter/README.md) внутри
доски, скачайте JSON **всей доски** и выберите его в поле **Web SDK JSON**. GUI
передаст файл в строгий конвейер объединения REST и Web SDK. Capture другой
доски или устаревший capture отклоняется. Если поле пустое, выполняется только
REST-экспорт.

## Автоматизация кодом

Выберите **Code automation** и один раз подключите Miro app. GUI сохраняет
только access token в системном хранилище текущего пользователя: Windows
Credential Manager, macOS Keychain или доступном Linux keyring. Client ID и
Client secret в файлы не сохраняются. Повторные запуски используют токен без
нового OAuth. Кнопки **Switch Miro team** и **Forget saved token** удаляют
сохранённый токен. Поддерживается одно подключение Miro на пользователя ОС.

Этапы GUI объясняет в журнале.

Если агент управляет браузером, но не может работать с окном GUI, запустите
`miro2obsidian setup-serve --port 8767` и откройте
`http://127.0.0.1:8767/`. Перенесите Client ID и Client secret своего Miro app
в локальную форму и завершите OAuth в том же браузере. Форма доступна только
через loopback, держит credentials в памяти до завершения OAuth и сохраняет в
системном хранилище лишь полученный access token. Агент может использовать
кнопки Copy/Paste без чтения значений. После подключения остановите сервер;
повторные запуски используют `--stored-token`.

Для запуска по расписанию используйте CLI с `--stored-token` под той же
учётной записью ОС:

```powershell
miro2obsidian --stored-token `
  --board-id <board_id> `
  --source-json <vault>\_miro_sources\board.json `
  --target-dir <vault>\Canvas `
  --vault-root <vault> `
  --format miro-canvas
```

Команду можно поместить в Windows Task Scheduler, launchd или cron. Если
системное хранилище недоступно, задайте `MIRO_ACCESS_TOKEN` в окружении
процесса и не используйте `--stored-token`. Если Miro отзовёт токен или app
будет удалено из team, потребуется повторное подключение. Сейчас
режим кода делает автономный REST-экспорт. Web SDK добавляется, только если в
поле **Web SDK JSON** задан свежий capture всей доски; сам браузер этот режим
пока не управляет. Встроенный сервер Web SDK запускается командой
`miro2obsidian websdk-serve --port 8766`.

## Агентный режим

Выберите одну доску Miro или её URL и режим **Agent**. Для любого локального
агента задайте `MIRO2OBSIDIAN_AGENT_COMMAND` как JSON-массив исполняемого файла
и аргументов либо введите тот же массив через **Configure agent** в GUI.
Программа получает один JSON-запрос через stdin и возвращает
один JSON-ответ через stdout. Оболочка не используется. Запрос содержит
`protocol_version: 1`, адрес доски, пути vault и результата, формат, команды
`pipeline_command` и `websdk_server_command`, временный `browser_cdp_url`,
текст задачи и схему ответа.
Ответ содержит `status` (`complete`, `needs_user` или `failed`),
`artifact_path`, `source_json` и необязательную причину `reason`; пути
абсолютные при успехе, иначе `null`. Причина может быть
`browser_unavailable` или `agent_network_unavailable`. Это общий протокол для любого агента с
доступом к CDP браузера.

Режим Agent открывает отдельный профиль Chromium в каталоге данных текущего
пользователя ОС. При следующих запусках профиль используется снова. Случайный
локальный CDP-порт доступен только пока работает агент. Первый вход в Miro или
MFA в новом профиле остаются за владельцем аккаунта. Программа сначала
проверяет сессию через страницу досок, при необходимости открывает страницу
входа Miro и ждёт до пяти минут до запуска агента. Вход в другом браузере не
переносится. Если вход не завершён, возвращается `needs_user: login`; после
входа запустите режим Agent снова. Если подходящего браузера
нет, программа устанавливает Chromium через Playwright. Если адаптер уже
управляет собственным браузером, задайте `MIRO2OBSIDIAN_AGENT_BROWSER=external`:
тогда `browser_cdp_url` будет `null`. Переменная
`MIRO2OBSIDIAN_BROWSER_PROFILE` задаёт другое место хранения профиля. Не
указывайте обычный профиль Chrome.

Miro Desktop необязателен. Режим Agent использует отдельный Chromium и при
установленном Desktop, и на ПК, где доступен только браузер. В ручном режиме
можно экспортировать через Miro Desktop, если там работают вход и app-экспортёр.
Вход в Desktop не авторизует отдельный профиль Chromium.
[Матрица проверки этого ПК](ENVIRONMENT_TEST_MATRIX.ru.md) показывает, какие
варианты действительно пройдены.

Если переменная не задана, установленный локально Codex CLI используется
как адаптер по умолчанию. Это работает и с готовой сборкой, если рядом с GUI
есть `miro2obsidian` CLI. Секреты Miro не попадают в
запрос, аргументы, окружение дочернего процесса или журнал GUI. GUI принимает
успешный результат только внутри выбранной папки Canvas, после проверки
Canvas, вложений и свежего полного источника REST/Web SDK.

Встроенный адаптер Codex получает тот же CDP-адрес. Ему не требуется браузер
этого чата, но его Python/Playwright окружение должно иметь доступ к loopback.
При `MIRO2OBSIDIAN_AGENT_BROWSER=external` прежняя предварительная проверка
браузерного инструмента возвращает `browser_unavailable`, если он недоступен.
Если агент не может связаться со своим сервисом, он возвращает
`agent_network_unavailable`. Браузер, привязанный к этому чату, не становится
автоматически доступным отдельной CLI-сессии агента. Для живого запуска
открывайте готовый GUI с рабочего стола: дочерний процесс внутри сетевой
песочницы Codex наследует её ограничение.

Miro может потребовать вход, MFA, согласие на права или разрешение
администратора team. Тогда агент сообщает `needs_user`; обходить эти требования
он не должен. В [опубликованной инструкции Miro](https://developers.miro.com/docs/build-your-first-hello-world-rest-api-app)
developer app создаётся в Developer Dashboard, поэтому автоматическое создание
app требует доступа к интерфейсу браузера. Режим кода запускается после
подключения app. Выбранный vault должен быть доступен агенту для записи. Агент
запускается в отдельной сессии: браузер и авторизация этого чата могут быть
недоступны. Режим работает с одной доской за запуск. Готовая сборка может
использовать внешний адаптер или локальный Codex CLI.

## Известное ограничение

[Матрица проверки Windows](ENVIRONMENT_TEST_MATRIX.ru.md) описывает случай,
когда отдельный Chromium перешёл по URL доски, но остался на экране загрузки
Miro. Текущая проверка входа по URL не доказывает готовность элементов доски.
Перед сообщением об успешном новом захвате Web SDK агент должен проверить
загруженный интерфейс. Если app отсутствует в Tools этого браузера, используйте
режим кода с отдельно проверенным JSON всей доски.

REST и Web SDK Miro не открывают все детали неподдерживаемых объектов доски.
Валидный Canvas — проверенный экспорт публичных API, а не полная резервная
копия Miro. На этом Windows-ПК открытый Obsidian удерживал только что созданный
Canvas и вызвал `WinError 5` при последующей перезаписи. Закройте Canvas в
Obsidian и повторите запуск; используйте результат только после успешного
завершения конвейера.
